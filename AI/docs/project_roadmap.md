# 최종 마무리까지의 작업 로드맵

## 완료 기준

최초 목표였던 공개 데이터 연구, 직접 학습한 baseline, 한계 분석, LSTM 또는 Transformer 개선 모델, 성능·지연시간·메모리 비교, 실제 TCP 서버 추론 연동과 포트폴리오 문서까지 포함한다. 단순히 dummy 응답이 오거나 학습 모델 하나를 연결한 상태를 최종 완료로 정의하지 않는다.

현재 **운영 메시지 데이터셋 구성 및 run/session 단위 분리까지 완료**했다. 이 단계를 포함하면 8개 작업 묶음이며, 이 단계가 끝난 현재 **7단계가 남는다**. 단계는 구현·실험 묶음 수이지 작업 일수나 실행 명령 수가 아니다. 데이터나 관측을 개선해야 하면 앞 단계로 돌아가 반복할 수 있다.

## 현재까지 완료

- C++ observer·feature 추출·bounded queue·HTTP worker와 dummy 결과 저장
- FastAPI v2 입력 검증과 Python 책임 분리
- UNSW-NB15 EDA·전처리·LR/RF 직접 학습·오분류·비교·validation 선정 실험
- 공개 데이터와 운영 feature 의미의 비호환 분석 및 운영 명세 확정
- 오류 경로 보강, 종료 snapshot 고정과 자동 테스트
- 독립 정답을 보존하는 비동기 JSONL 수집기
- 정상/통제된 이상 생성기와 21개 run 수집·품질 검증
- 운영 메시지 406건, run/session 비중복 train·validation·test 및 재현 manifest

## 단계별 주의점

1. 운영 baseline은 UNSW 모델을 이름만 맞춰 가져오지 않고 현재 입력 7개로 새로 학습한다. scaler fit은 train만, 설정·threshold 선택은 validation만 사용한다. 이 단계에서 test를 성능 선택에 사용하지 않는다.
2. 현재 숫자형 입력으로 관측할 수 없는 본문 이상, 생성기 특성에 적응하는 편향, 작은 독립 run 수를 분석한다. 추가 데이터나 새 feature가 필요하면 독립 정답·새 의미 버전·재수집·분할까지 같이 설계한다. 오류 수로 정답을 만들지 않는다.
3. 임의 UNSW 행을 시간 순서로 연결하지 않는다. 이미 분리한 각 split의 동일 run/session 안에서 시계열 창을 만든다. 1개 메시지 뒤 종료되는 이상 시나리오의 padding·mask·판단 가능 시점과 coverage를 기록한다.
4. validation에서 실험과 모델 후보를 고정한 뒤 test를 최종 비교에 사용한다. 시계열 모델과 단일 메시지 모델의 판단 시점·평가 대상이 다르면 coverage를 따로 공개한다. 개선이 없다면 그 결과와 원인을 정직하게 기록한다.
5. LSTM이 아니라 RF가 최종 선택될 수도 있다. 비교 결과에 따른 선택 모델을 연결하고, 의미 버전·입력 순서·전처리·threshold를 산출물과 함께 고정한다. 실시간 경로에 필요한 상태 관리도 선택 모델 기준으로 검증한다.
6. HTTP 오류나 AI 지연이 TCP I/O를 막지 않는지 확인한다. 관리자용 전체 웹 대시보드는 필수 범위에 넣지 않으며 기존 세션별 결과 저장을 이용한 최소 조회·시연을 준비한다.
7. 통제된 애플리케이션 메시지 이상과 실제 네트워크 침입 탐지를 구분해 설명한다. 기존 공개 데이터 연구 결과와 운영 모델 결과를 한 성능 숫자로 합치지 않는다.

## 바로 다음 작업

`training`에 운영 LR/RF 학습 진입점을 추가하고 고정 데이터셋 manifest·입력 순서·파일 해시를 검증한다. train으로 전처리와 모델을 fit하고 validation의 제한된 후보·threshold 결과를 보관한다. 기존 UNSW 산출물은 덮어쓰지 않는다.

초기 데이터 규모만으로 최종 성능이나 일반화를 보장하지 않는다. 로드맵은 완료 조건을 명확히 한 것이며, 7번의 수정만 하면 무조건 완성된다는 일정 약속은 아니다.
