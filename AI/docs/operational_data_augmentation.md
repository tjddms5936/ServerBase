# 독립 운영 데이터 보강 설계

## 상태와 목적

이 문서는 오분류 분석 단계에서 고정한 사전 설계다. 후속 구현에서 생성기 제어·캠페인 holdout과 **6개 캠페인·84개 run 실제 수집·검증**을 완료했다. 모델 학습·새 데이터 예측은 아직 하지 않았다. 구현·실제 결과는 `docs/operational_augmentation_collection.md`, `reports/operational_augmentation_collection.md`를 참조한다.

`configs/operational_augmentation_plan.json`은 기존 `CampaignPlan` 설정과 다른 설계 문서이며 기존 수집 명령에 그대로 넣을 수 없다. 새 `collect_operational_augmentation.py` 명령이 이 설계를 실행 가능한 v2 계획으로 변환한다. JSON의 `design_only` 상태와 아래의 구현 예정 표현은 작성 시점의 설계를 보존한 것이다.

목적은 선택된 Validation의 숫자를 반복 조정하는 것이 아니라, 실행 조건이 다른 캠페인에서 현재 모델의 한계를 검증하고 후속 모델을 위한 개발 데이터를 확보하는 것이다. 실제 외부 공격·실서비스 트래픽을 대표하는 데이터 확보라고 주장하지 않는다.

## 분석에서 얻은 가설

| 관찰 | 개선 가설 | 확인할 근거 |
| --- | --- | --- |
| 정상 묶음의 짧은 파싱 간격에서 FP | 묶음 크기·타이밍의 정상 사례 보강이 필요할 수 있다. | 새 정상 묶음 Validation의 FPR, 여러 독립 run의 사례 |
| burst 네 세션 첫 네 메시지 FN | 초기 prefix와 응답 누적값에 모델이 의존할 수 있다. | 첫 탐지 위치·prefix별 FN, 길이가 겹치는 정상·이상 |
| burst Train/Validation 연결 시간 차이 | 실행 스케줄·동시 연결·프로세스 초기화 편향이 있을 수 있다. | 실제 관측 시각과 실행 환경, 교차 배치 캠페인 결과 |
| 너무 짧은 본문 네 건 FN | 크기 단서가 있어도 선택된 모델·정책이 활용하지 못했다. | 기존 프로토콜 거부와 AI 판단을 분리한 보고 |
| 같은 크기의 잘못된 문자열 길이 | 본문 정보를 전달하지 않는 현재 표현은 유효성 보장에 부족하다. | 구성 반례·정상 크기와 겹치는 malformed 사례 |

가설은 검증 대상이지 확인된 원인이 아니다. 데이터를 더 모은다고 누락된 정보를 복원할 수는 없다.

## 캠페인별 사전 분할

| 슬롯 | seed | 목적 |
| --- | ---: | --- |
| development_01 | 101 | Train |
| development_02 | 211 | Train |
| development_03 | 307 | Train |
| selection_01 | 401 | Validation |
| holdout_01 | 503 | Test |
| holdout_02 | 607 | Test |

슬롯은 계획상의 이름이다. 실제 수집 시 별도 campaign_id를 발급하고 슬롯·seed·split 참조를 manifest에 기록한다. 슬롯의 전체 반복·run·session·message가 같은 split에 속해야 한다. 생성 결과나 모델 점수를 보고 역할을 바꾸지 않는다.

각 캠페인은 기존 7개 시나리오를 2번 반복하고 run마다 세션 4개를 사용한다. 계획 총량은 **캠페인 6개·run 84개·세션 336개**다. 헤더 거부 12개 run·48개 세션은 메시지가 없으므로 메시지 모델의 후보는 run 72개·세션 288개다. 실제 메시지 수와 정답 비율은 생성 뒤 품질 보고서에 기록하며 여기서 임의로 확정하지 않는다.

새 seed·실행·서버/API 프로세스 재시작은 새 원본 확보의 조건이다. 기존 CSV에 이름만 새로 붙이거나 복사해 독립 데이터로 만들지 않는다. 같은 장비·같은 생성기를 사용하는 한 그 도메인 편향은 남는다.

설계 당시 데이터셋 분리기는 반복 묶음 단위였다. 그대로 적용하면 하나의 새 캠페인 반복이 여러 split에 들어갈 수 있다. 후속 구현에서 **사전 캠페인 배정 정책과 새 데이터셋 버전**을 추가했고 기존 v1은 보존했다.

## 생성기 보강 제어

다음 설정을 명시적으로 지원하고, 시나리오·split에 일대일로 고정되지 않도록 사전에 교차 배치한다.

- 본문 문자열 크기: 8·24·96·384·768바이트
- 정상 세션의 메시지 수: 6~24개, burst: 12~24개. 긴 세션이라는 사실만으로 정답이 정해지지 않도록 범위를 겹친다.
- 정상 요청 간 의도적 대기: 1~4ms·5~15ms·20~40ms; 통제된 burst는 무대기. 이는 실험 정책이며 실제 공격 판별 규칙이 아니다.
- 정상/행동 이상에 묶음 크기 1·4·8과 연결 동시성 1·2·4를 교차 배치한다. 시나리오별 의미와 정책을 명확히 기록한다.
- 정상 분할 송신의 조각 크기: 7·19·31바이트
- 시나리오 실행 순서: 캠페인 seed에 따른 사전 순서로 배치하고 동일 시나리오가 항상 같은 실행 위치에 오지 않게 한다.

설계 당시 `run_session()`은 일부 묶음 크기 4·조각 크기 31을 고정했다. 후속 구현에서 필드·범위 검증·기대값 생성·실제 송신·자동 테스트와 sendall 호출 계측을 추가했다. 단순히 JSON에 값을 적어 실제 송신이 바뀌었다고 주장하지 않는다.

송신 계획의 대기 시간과 실제 수신/파싱 시간은 같지 않다. OS 스케줄링과 IOCP 묶음 처리를 포함한 실제 C++ 관측을 보관하고, 프로세스 시작·OS/빌드·설정·동시 연결 상태를 비교 근거로 기록한다. 실행 환경 metadata는 추적용이며 자동으로 모델 입력에 합치지 않는다.

## 정답·관측·프로토콜 경계

정답은 송신 전에 고정한 시나리오·행동 정책 manifest에서 가져온다. AI 예측, error_count, 종료 summary와 오분류 결과로 정답을 만들거나 바꾸지 않는다. 아직 증거가 부족한 초반 burst 메시지도 사후에 정상으로 바꾸지 않는다. 이후 판단 가능 시점·prefix coverage를 명시한다.

현재 v2에서 먼저 수행할 수 있는 것은 동일한 7개 입력의 조건을 다양화해 일반화 한계를 측정하는 일이다. 일부 입력 정보를 추가하려면 별도의 변경 가설과 비교 조건을 고정해야 한다.

프로토콜 유효성은 기존 C++의 결정적 파싱·거부 경로로 다루고, AI의 행동 이상 판단과 분리해서 보고하는 구조를 우선 검토한다. 헤더 거부·본문 실패를 이미 검출하는 코드를 새 AI 성능처럼 계산하지 않는다. 현재 통합 정답을 사후 삭제하는 것도 아니다. 기존 목표의 시나리오별 성능을 공개하고, 새로운 과제 범위가 필요하면 별도로 정의한다.

본문 길이 필드나 검증 결과를 추가하는 v3를 선택한다면 observer 이벤트·입력 의미·판단 시점·API schema·수집과 학습 데이터를 함께 바꿔야 한다. 검증 뒤 알게 된 값을 v2의 이전 snapshot에 덧붙이지 않는다. 기존 LSTM에도 없는 본문 정보를 기대하지 않는다.

## 품질 게이트

1. 시나리오·슬롯·seed·split·생성기/빌드/계약 버전·독립 정답을 수집 전에 저장한다.
2. 실제 JSONL을 사전 송신 기대값과 대조해 누락·중복·세션 식별자·응답·정상 종료를 검증한다.
3. 불완전 run과 헤더 거부를 구분하고 이유를 보관한다. summary로 가짜 메시지를 생성하지 않는다.
4. 시나리오별 메시지·세션·정답 분포, 크기·타이밍 범위와 교차 split의 campaign/run/session/row 중복을 보고한다.
5. 창은 split 구성 후 동일 run/session 내부에서 만든다. 캠페인·세션·split 경계를 넘는 창을 금지한다.
6. Test에는 형식·유실 품질 검사만 수행한다. 모델 점수·오분류·feature 선택에는 사용하지 않는다.

목적지는 `127.0.0.1:4000`으로 제한한다. 세션당 메시지 최대 24개, run당 세션 최대 4개, 동시 연결 최대 4개, 문자열 최대 768바이트다. 외부 송신·무제한 부하는 허용하지 않는다. 이 설계 문서 자체는 송신을 시작하지 않으며 명시적으로 새 수집 명령을 실행해야 한다.

## 새 실험의 순서

먼저 현재 선정 모델 해시와 threshold 0.7을 고정한다. 새 데이터의 Validation에서만 기존 모델을 진단하고, 그 결과와 조건을 보고한다. 새 Test는 최종 평가까지 보류하며 기존 v1 Test도 건드리지 않는다.

보강 모델은 새 Train 캠페인만으로 전처리와 모델을 fit한다. 새 Validation의 제한된 후보·선택 기준은 후속 실험 전에 따로 고정한다. 이전 데이터와 새 데이터를 합치거나 feature 의미를 바꾸려면 버전·역할·평가 대상의 변화를 먼저 명시한다.

이후 실제 같은 세션 prefix 창과 LSTM을 비교할 수 있다. 단일 메시지·시계열 모델의 판단 시점, 짧은 세션 처리, 처음 탐지까지의 메시지 수·시간 및 coverage를 같이 보고한다. 일반화나 성능 개선이 없으면 그 결과도 그대로 남긴다.

## 구현 이후 다음 작업

생성기의 명시적 제어·교차 배치와 사전 캠페인 분리, 수집·품질 검증, 고정 기존 모델 진단과 새 Train 전용 보강 학습·선정·비교까지 완료했다. 진단은 `docs/operational_frozen_baseline_audit.md`, 후속 실험은 `docs/operational_augmentation_experiment.md`에 정리했다. 로드맵 2단계를 마쳐 큰 작업 묶음은 5개다. 다음은 동일 run/session 내부의 시계열 창 구성과 LSTM 개선 실험이다.
