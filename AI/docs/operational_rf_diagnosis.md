# RF 오탐 진단과 보정 실험 준비

## 지금 한 일

이번 단계는 **왜 정상 묶음 메시지를 이상으로 판단했는지 단서를 찾고, 다음 보정 실험을 준비한 작업**이다. 아직 정상 오탐을 줄이는 새 모델을 학습한 단계가 아니다.

기존 RF leaf=5·threshold=0.3을 변경하지 않고 Train 1,538건과 Validation 513건을 재예측했다. 모델·입력·기존 지표·행별 확률을 대조했고 Validation FP 30건·FN 9건이 그대로 재현됐다. Test CSV와 최종 Test 예측 CSV는 열지 않았다. 이미 사용한 Test의 RF 승인 보류는 기존 최종 JSON 보고서에서만 인용한다.

이 설계는 기존 Test 결과를 본 뒤 시작한 개선 계획이다. 최초 평가 전에 등록된 가설이나 보정 효과의 독립 검증이라고 주장하지 않는다.

## 찾은 단서

Validation의 정상 묶음 130건 중 오탐은 21건으로 FPR 16.15%였다. 정상 일반 전송은 7/110건, 조각 전송은 2/109건이었다.

정상 묶음 오탐 21건의 파싱 간격 중앙값은 0.041ms, 최댓값은 0.134ms였다. 첫 메시지 5건은 비교할 이전 메시지가 없어서 간격이 0이다. 나머지 오탐 16건은 모두 1ms 이하이며 이전 메시지와 누적 수신 바이트가 같았다. 정상 묶음의 후속 1ms 이하 구간 48건 중 오탐이 16건이었다. 반대로 1ms를 넘는 후속 정상 묶음에서는 이번 Validation의 오탐이 없었다.

같은 Validation의 burst도 대부분 1ms 이하 구간에 있었다. RF의 학습된 불순도 감소 중요도는 연결 지속 시간 42.81%, 순간 파싱 간격 39.25%로 시간 관련 입력 합계가 82.07%였다. 이는 **파싱 시점의 짧은 간격을 과도하게 활용할 가능성**을 뒷받침하는 단서이지, 원인이나 개별 판단의 기여 비율을 확정하는 증거는 아니다. `packet_size`와 `payload_size`처럼 강하게 연결된 입력도 있어 중요도는 단독으로 해석하지 않는다.

Train의 FP 113건·FN 0건도 함께 보관한다. Train FPR 10.77%는 일반화 점수가 아니며 threshold=0.3에서 학습 자료도 모두 맞추지 못한다는 참고 관측이다.

## 서버 수집 의미를 유지하는 이유

`Session::OnRecv_v2`는 실제 수신 바이트를 기록한 뒤 `ParsePackets`를 호출한다. `FeatureCollector::HandleRecvCompletedLocked`는 수신 완료의 전체 바이트를 누적하고, `HandlePacketParsedLocked`는 메시지별 snapshot을 만든다.

예를 들어 100바이트 프레임 4개가 한 번에 수신되면 첫 메시지의 누적 수신량에도 400바이트가 반영될 수 있다. 네 프레임을 연속 파싱하면 메시지 간격도 매우 짧아질 수 있다. 이것은 실제로 이미 수신한 정보를 기록한 것이므로 코드 오류나 미래 시각의 데이터 누출로 단정하지 않는다.

다만 다음 값들은 다르다.

- 누적 수신 바이트: 소켓 수신 완료에서 이미 받은 바이트 합.
- 현재까지 파싱한 바이트: 관측한 메시지 프레임 크기의 과거·현재 합.
- 순간 파싱 간격: 이전 메시지와 현재 메시지의 파서 실행 시각 차이.
- prefix 평균 간격: 첫 메시지를 제외한 과거·현재 파싱 간격의 평균.

누적 수신량이 같은 행만으로 TCP 패킷 경계나 수신 완료 id를 완전히 복원하지 않는다. 파싱 간격을 클라이언트 송신 간격으로 이름만 바꾸지도 않는다. 현재 C++ 코드와 FastAPI v2 계약은 수정하지 않았다.

## 입력 보정 후보

모델 종류는 RF로 유지하고 입력 표현만 단계적으로 바꿔 비교한다. 트리 수 100, 최소 leaf 5, seed 42, 계산 병렬도 1도 유지한다.

| 후보 | 입력 | 확인할 가설 |
| --- | --- | --- |
| `rf_raw7` | 기존 원본 7개 | 새 데이터만으로 얻는 변화의 대조군 |
| `rf_without_io5` | 누적 송수신량을 뺀 5개 | 소켓 완료 누적량을 제외하면 정상 묶음 오탐이 줄어드는가 |
| `rf_prefix_mean5` | 위 5개에서 순간 간격을 prefix 평균으로 교체 | 짧은 묶음 내부 간격 대신 이전 정상 대기도 참고하면 도움이 되는가 |
| `rf_prefix_mean_parsed6` | 평균 간격 후보에 파싱 프레임 크기 합 추가 | 수신 완료 누적량 대신 메시지 경계에 맞춘 누적량이 도움이 되는가 |

평균 간격은 `이전까지의 간격 합 + 현재 간격`을 `현재 request_index - 1`로 나눈다. 첫 메시지는 0이다. 전체 세션 평균이나 종료 summary를 쓰지 않으며 뒤쪽 메시지를 참조하지 않는다. 그룹별로 순서를 정렬한 뒤 원본 행 순서를 유지하고, 오프라인 입력의 누락·중복·counter 역행은 거부한다. 이 정렬이 실시간 경로에서 역순 도착을 무조건 허용한다는 뜻은 아니다.

현재 원본 v2 JSON은 그대로 둔다. 모델 입력 표현은 `raw7_v1`, `without_io5_v1`, `prefix_mean5_v1`, `prefix_mean_parsed6_v1`로 별도 버전 관리한다. 새 파생 값은 별도 이름을 사용하고 원본 필드에 다른 의미를 덮어쓰지 않는다. 지금 구현은 오프라인 Train/Validation 변환이며 실시간 상태 모듈이나 승인된 Test 변환기가 아니다.

첫 정상 묶음에는 이전 정상 대기가 없으므로 평균을 써도 burst와 구분하지 못할 수 있다. 본문이 같은 크기인 malformed도 입력만으로 항상 구분할 수 없다. 후보가 개선된다는 보장은 없고 결과를 확인한 뒤 채택한다.

## 새 캠페인과 선정 규칙

새 seed의 캠페인 6개를 Train 3개·Validation 1개·Test 2개로 **수집 전에** 배정한다. 각 캠페인에서 정상 묶음 크기 1/4/8과 정상 대기 범위 1~4/5~15/20~40ms의 9조합을 모두 실행한다. burst는 같은 반복에서 묶음 크기·동시성·크기 및 메시지 수 범위를 맞추고 지정 대기만 0으로 둔다. 동일 범위를 쓰는 것이 모든 실제 프레임·관측 시각까지 동일하게 만든다는 뜻은 아니다.

7개 시나리오·9회 반복·캠페인 6개로 계획 run은 378개, 세션은 1,512개다. 기존 생성기의 송신 전 기대값을 계산하면 메시지는 Train 7,976건·Validation 2,737건·Test 5,407건이다. **모두 계획 값이며 실제로 수집한 건수가 아니다.** 헤더 거부는 메시지 0건인 별도 관측 coverage로 유지한다.

새 Train만으로 후보 4개를 학습하고 threshold 0.3/0.4/0.5/0.6/0.7의 20개 조합을 새 Validation에서 비교한다. 이전 RF는 그대로 새 Validation에 적용해 별도 기준선으로 보고하며 20개 신규 후보 조합에 포함하지 않는다.

전체 FPR 10% 이하·Recall 50% 이상에 더해 정상 묶음 FPR도 10% 이하를 요구한다. 제약 통과 조합 중 Recall 최대, F1 최대, FPR 최소, 후보 id와 threshold 오름차순으로 하나를 고른다. 비용은 기존 p95 25ms·프로세스 최대 RSS 512MiB·필수 파일 50MiB 이하를 유지한다. 상태형 후보의 전체 판단 비용에는 온라인 prefix 갱신도 포함해야 한다.

새 Validation·비용으로 후보를 잠근 뒤 새 Test에서 그 후보의 승인 여부만 확인한다. 비용 실패 또는 통과 후보 없음이면 새 Test를 열지 않는다. 기존 Test를 새 후보 선정이나 독립 승인에 재사용하지 않으며 Test에서 더 좋은 후보로 교체하지 않는다.

실제 수집 전에 캠페인 id·계획·정답·실행 코드·빌드·기준 모델·설계 해시를 추가로 잠가야 한다. 이번 설계 컴파일은 그 실행 잠금을 대신하지 않는다. 실제 메시지 누락·중복·split 비중복과 큐 유실 검사도 실제 수집 이후에 해야 한다.

실제 실행에서는 학습 함수·Test 원본/최종 예측 CSV·raw JSONL 접근·네트워크 송신을 금지한 상태로 완료했다. 단위 테스트와 전체 회귀 테스트 결과는 커밋 정리 문서에 기록한다.
